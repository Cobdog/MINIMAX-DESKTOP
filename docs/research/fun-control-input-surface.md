# MiniMax-H3 Fun Control — the exact input surface, pose format, extraction tooling, and the in-app rig question

> Compiled 2026-09-14 (Flux task `p7nff5s`). Viability pass for the maintainer's promotion of MiniMax-H3-Fun-Controlnet-Union to first-class with its own authoring toolchain. Builds on `docs/research/h3-sampler-shaping-and-motion-control.md` §2.2 (specs already pinned there are not re-derived) and `docs/research/h3-node-ecosystem-sweep.md` (T8mars context). Method: **code-read, not README-trusted** — the local testbed's ComfyUI core (`/home/agent/work/VS Proj/Kreatine/testbed/ComfyUI/`, v0.34.0) plus the trainer's own repo (aigc-apps/VideoX-Fun, Apache-2.0) and the released demo assets were inspected directly. Tags: **[DOC]** verified in shipped code / official source (including my code reads and asset inspections), **[COMM]** reputable community finding, **[SPEC]** plausible-unverified, **[UNK]** nobody documents it.
>
> **Headline verdicts:** the wire format is a *plain RGB image-batch per frame* — VAE-encoded, content determines the control kind, no type embedding, no keypoint pathway; the pose format is the **DWPose whole-body colored-skeleton render** (verified from the trainer's own vendored draw code + their demo asset); **non-human pose generalization is UNK** and one cheap experiment on 8189 settles it; extraction for every kind is **server-drivable with zero or near-zero new dependencies** (pose/depth/canny are now *native* ComfyUI core nodes — verified in our testbed); the in-app IK rig is **buildable small** — and ComfyUI core already ships the two halves of the round-trip (a keypoint→skeleton-render node and a 3D-body→OpenPose-2D re-projection exporter) that de-risk it.

## 2. Input-spec card per control kind

All kinds share the transport: **RGB image-batch (T,H,W,3), same resolution as the target video, frame count on the 17n+5 grid (≤15 s), 24 fps, multiples-of-32 canvas, H3-VAE-encoded** [DOC]. The kinds differ only in what the frames should *depict*:

| Kind | Frame content | Official extractor (trainer's repo) | Best extractor in our stack | Notes |
|---|---|---|---|---|
| **canny** | White edges on black (RGB- replicated grayscale) | `VideoToCanny` — cv2.Canny, low 100 / high 200 ([nodes.py](https://github.com/aigc-apps/VideoX-Fun/blob/main/comfyui/annotator/nodes.py)) **[DOC]** | **Native `Canny` node** ("Detect Edges"), already used by our Z-Image path. Same cv2 thresholds (our app ships 0.1/0.32 normalized ≈ 25/82 — closer to the official 100/200 is worth a bake-off) **[DOC]** | The only kind with zero dependencies and zero weight downloads |
| **depth** | Depth map as RGB (grayscale replicated); the repo's own node outputs ZoeDepth | `VideoToDepth` — **ZoeDepth** (ZoeD_M12_N) at 512 padded res **[DOC]** | **Native Depth Anything 3** (`LoadDA3Model`→`DA3Inference`→`DA3Render`, verified in testbed core) or aux `DepthAnythingV2Preprocessor` (DAV2-Large **already staged** in testbed) **[DOC]** | Trainer used ZoeDepth; community H3 workflows use DepthAnything — both are "a depth map", the union checkpoint should treat them as the same signal family (Zoe vs DA color/scale mismatch is a real variable — worth one A/B) **[COMM]** |
| **pose** | **DWPose whole-body colored skeleton on black** (§3) | `VideoToPose` — DWPose ONNX (yolox_l + dw-ll_ucoco_384), renders body+hands+face always, 512 padded **[DOC]** | **Native SDPose** (`SDPoseKeypointExtractor` + `SDPoseDrawKeypoints`) or aux `DWPreprocessor` (TorchScript backend **already staged**, onnxruntime NOT needed — default ckpt is `dw-ll_ucoco_384_bs5.torchscript.pt`) **[DOC]** | The one kind where the *render spec* matters exactly (palette/limb style) — see §3. SDPose emits OpenPose-format keypoint JSON as a node output, which is also the rig bridge |
| **HED** | White soft edges on black | (in union training set; no repo node shipped) | aux `HEDPreprocessor` (weights auto-download from lllyasviel/Annotators on first use — **not pre-staged** in testbed) **[DOC]** | Untested by the community on H3 specifically (wyzborrero: "canny/HED/MLSD are in the union model's training set but untested") **[COMM]** |
| **MLSD** | White straight-line segments on black | (in union training set) | aux `MLSDPreprocessor` (auto-download, not pre-staged) **[DOC]** | Same untested-on-H3 caveat **[COMM]** |
| **inpaint** (union) | No control frames required; `mask` (1 = regenerate, 0 = keep) + `source_video` behind the mask | `--enable_inpaint` training layout; `inpaint_video` / `inpaint_video_mask` ("white = repaint, black = keep") in predict script **[DOC]** | Native `MiniMaxH3FunControlNetApply` mask/source inputs; ComfyUI builds the visibility+masked-latent channels itself **[DOC]** | Composable **with** any control video (that's what the 49-dim layout is for). Mask-less checkpoints reject inpaint inputs outright (layout mismatch) |
| **custom** (de-facto) | Anything: sprites, colored regions, box outlines | — (not trained; the zero-gated branch accepts any RGB) | T8mars `MiniMaxH3TrajectoryControlRenderT8Advanced` renders reference_sprite / soft_region / box_outline control videos **[COMM]** | The shipped evidence that off-distribution control content still *steers* ("steers the composition rather than perfect frame control") — the load-bearing precedent for non-human experiments |

**Apply-node surface (native, exact):** `strength` (default 1.0, max 10), `start_percent` (0.0), `end_percent` (1.0), `control_video` (optional IMAGE), `mask` (optional, "1 marks the regions to regenerate"), `source_video` (optional, only read when mask given); strength==0 or control+mask both absent ⇒ no-op. The control branch is active only while `sigma_end ≤ σ ≤ sigma_start`; **audio rows always get zero control skip** (code: `skip[audio_pos] = 0`) **[DOC — nodes_minimax_h3.py:563-605, 501]**. T8mars' wrapper adds `fit_mode` (exact/center_crop/stretch, lanczos) and `control_kind` (depth/pose/canny/HED/MLSD/custom — **bookkeeping only**, "getting this wrong is a silent quality hit, not an error"; the wire format never changes) **[COMM comfy.icu]**.

**Checkpoint variant trap:** two adaln forms exist; ComfyUI detects via metadata (`minimax_h3_fun_controlnet == "adaln_basis"` → curve-form, time_embed_dim 8, else full-width 2688) and wyzborrero's loader "refuses the incompatible full-width original checkpoint"; RunComfy: "must use the curve-form Union checkpoint" **[DOC code / COMM]**. The testbed already stages a quantized union branch: `models/model_patches/minimax_h3_fun_controlnet_union_pruned_int8_convrot.safetensors` (load via `ModelPatchLoader`) **[DOC local]**.

## 3. The pose format + the non-human verdict

### 3.1 Exact pose spec (what an in-app rig must emit)

Verified from the trainer's own vendored code (`comfyui/annotator/dwpose_utils/`, "modified from Mikubill/sd-webui-controlnet" — the same lineage controlnet_aux uses) and visually confirmed against their demo asset:

- **Skeleton**: DWPose whole-body 133/134 keypoints — body 18 in OpenPose order (neck synthesized as midpoint of shoulders), feet 6, face 68, hands 21+21. The trainer's `draw_pose` **always** draws body + left hand + right hand + face on a black canvas **[DOC `dwpose_utils/__init__.py`]**.
- **Body render**: 17 limbs as filled rotated ellipses, `stickwidth = 4`, colors × 0.6; joints as radius-4 circles in full color. Exact 18-color palette in limb order: `(255,0,0) (255,85,0) (255,170,0) (255,255,0) (170,255,0) (85,255,0) (0,255,0) (0,255,85) (0,255,170) (0,255,255) (0,170,255) (0,85,255) (0,0,255) (85,0,255) (170,0,255) (255,0,255) (255,0,170) (255,0,85)` **[DOC `dwpose_utils/util.py`]**.
- **Hands**: 20 finger-bone edges per hand as 2-px lines, HSV rainbow by edge index **[DOC]**. **Face**: white dots + pink links **[DOC]**.
- My inspection of their `asset/pose.mp4` (frame 30): matches exactly — magenta face mesh, white face dots, blue hand clusters, teal/blue legs, green/gold torso, black background, ~120–150 visible dots **[DOC asset, inspected]**. Demo resolution 576×1024@30fps/153 frames — note the *demo* is 30fps content on a 24fps-generation model; the pipeline resamples.
- ComfyUI core's native render (`SDPoseDrawKeypoints` → `KeypointDraw.draw_wholebody_keypoints`) reproduces the same conventions with toggles (`draw_body/hands/face/feet/head`, `stick_width=4`, `face_point_size=3`, score threshold) **[DOC local `comfy_extras/nodes_sdpose.py`, `comfy_extras/pose/keypoint_draw.py`]**.

**No keypoint-JSON pathway reaches the model**: every apply path (native node, T8mars, wyzborrero, VideoX-Fun pipeline) consumes rendered frames. A rig MUST export the render. (Two render bridges exist to reuse rather than reinvent: aux `pose_keypoint_postprocess.py` → `decode_json_as_poses` (OpenPose *and* AP-10K JSON → image, Apache-2.0) and native `SDPoseDrawKeypoints` (POSE_KEYPOINT JSON → image).)

### 3.2 Non-human verdict

- **Training was human-only** for pose: yolox_l is a *person* detector; no animal/creature pathway exists anywhere in the trainer, card, or configs **[DOC by inspection]**.
- **Does zero-gated conditioning generalize to arbitrary skeleton renders?** **[UNK]** — no H3 test published. Three data points bound the answer:
  1. The union checkpoint demonstrably accepts off-distribution RGB (T8mars `custom` sprite/region modes "steer the composition" — the control branch is a generic video-conditioned skip injector) **[COMM]** — so non-human *content* won't be ignored.
  2. SD-era precedent: human OpenPose controlnets do not pose animals — that's why separately trained AP-10K controlnets exist ([huchenlei/animal_openpose](https://huggingface.co/huchenlei/animal_openpose), [JFoz/dog-cat-pose](https://huggingface.co/JFoz/dog-cat-pose), [JFoz AP10K dataset](https://huggingface.co/datasets/JFoz/AP10K-poses-controlnet-dataset); aux ships `AnimalPosePreprocessor` (RTMPose AP-10K, 17 quadruped keypoints) as the companion) **[COMM]**. Expect an H3 human-pose prior to *interpret* a quadruped skeleton as a distorted human rather than articulate a quadruped — that is the hypothesis to falsify.
  3. wyzborrero's README explicitly blesses hand-drawn and 3D-package control input ("an estimator over reference footage, 3D-package output, hand-drawn input … all work since it just takes an IMAGE batch") — only depth and pose have been *exercised* **[COMM]**.
- **Settling experiment E-FC1 (the one to run first; 8189 testbed, engine-rule compliant — probe first):**
  - **Setup**: fixed seed, one neutral prompt per arm ("A dancer moves across the room." / "A dog trots across the room." / "A strange tall creature walks across the room."), 39 frames @ 480×832, `res_multistep`+`simple`, shifts 12/3, **guidance 1.0, 40 steps** (card recipe; turbo/caches OFF per the pinned-row hazard), strength 0.8–1.0, end_percent 0.6. Control videos all built from **the same quadruped trot clip**:
    - **Arm A (baseline sanity)**: human DWPose render from a human dance clip via aux `DWPreprocessor` — confirms the whole path works in our harness (estimator round-trip error as the metric).
    - **Arm B (the question)**: `AnimalPosePreprocessor` (AP-10K) render of the dog trot — quadruped skeleton, AP-10K palette, correct format discipline (colored skeleton on black).
    - **Arm C (control for format-vs-semantics)**: hand/proc-authored *humanoid* skeleton mimicking the dog's torso trajectory (same screen-space motion, human topology) — separates "follows colored-skeleton structure at all" from "articulates a quadruped".
    - **Arm D (the shipped workaround)**: sprite/region composite of the dog (T8mars-style `custom`) — the known-good non-skeleton route as the ceiling for non-human motion.
  - **Metrics (CPU, scripted)**: output keypoint re-estimation (DWPose on A, AP-10K on B/D) → per-frame keypoint error vs the control video; manual tags: {quadruped rendered | humanized creature | ignored control}; centroid tracking for D. 2 seeds × 4 arms ≈ 8 gens.
  - **Decision**: if B drives a quadruped at keypoint-error parity with A's human baseline → the pose surface is topology-agnostic → the in-app rig supports creature skeletons natively. If B humanizes but C/D track → non-human posing ships as sprite/region mode (or a tiny AP-10K LoRA on the control branch later — the trainer is open-sourced, `--trainable_modules control`). If nothing tracks → non-human motion control stays prompt+guide-side.
- **Adjacent 5-minute test E-FC0.5** (zero GPU cost): POST a graph to 8189 whose `SDPoseDrawKeypoints` node receives `keypoints` as a **raw JSON literal** (OpenPose frame dicts) instead of a link. If validation accepts it, our rig can emit keypoint JSON and let the server render — palette-exact by construction. If rejected, the rig renders client-side (canvas → PNG frames), which is the robust default anyway **[SPEC — untested]**.

### 5.2 Verdict: buildable as a small in-app rig — recommended minimal architecture

**Contract first (this is the whole trick):** the model eats *rendered frames*. The rig's pipeline is `author → per-frame keypoint timeline → palette-exact DWPose-style render → IMAGE batch → MiniMaxH3FunControlNetApply.control_video`. Keypoint JSON never reaches the model; it's only the rig's internal representation (and optionally the server-render bridge).

1. **Data model**: per-frame OpenPose-134 dicts (18 body + 6 feet + 68 face + 21+21 hands) — the native SDPose format, so extraction, authoring, and rendering share one schema. Hands/face default to *procedural relaxed poses* auto-attached to wrists/head (they matter little at full-body framing — the training renders always include them, so emit plausible ones rather than none). Frame timeline snaps authoring keys to the 17n+5 grid (5/22/39/56… pixel frames), ≤15 s.
2. **Rig geometry — 2.5D, not pure 2D**: a 3D stick figure (three.js scene, ~20 bones) that the user orbits; IK = **analytic two-bone** for limbs + FABRIK/CCD chain for spine-neck; drag targets are projected onto a user-facing plane. 3D buys correct foreshortening and limb-crossing depth ordering that pure-2D rigs get wrong and the model *will* read. Render = orthographic project to canvas at target resolution. (Pure-2D v0 is a viable de-scope for a first spike; 2.5D is the product.)
3. **Renderer — client-side canvas, palette-exact** (§3.1 spec): 18-color limb ellipses ×0.6, r-4 joints, HSV-rainbow hands, white face dots, black background, stickwidth 4. Export PNG frames (or WebP batch) → upload → `LoadImage`-batch or `LoadVideo`. This makes the round-trip exact against the training distribution *by construction* and keeps the server dependency-free. Optional server mode (after E-FC0.5 passes): emit keypoint JSON → native `SDPoseDrawKeypoints`.
4. **Skeleton templates are pluggable**: human-134 default; AP-10K quadruped (17 kp) template ready if E-FC1 arm B wins; free-form creature template (arbitrary colored graph) if the model proves topology-agnostic. The renderer is dumb — the template defines joints/limbs/palette.
5. **Input modes** (cheapest first): preset pose/animation library (PoseMy.Art-style; seed from Mixamo BVH → keypoint bake, or from SAM3D-body extraction of stock footage); *pose-transfer from reference video* (existing extraction pipeline §4 — no rig needed); webcam mocap via MediaPipe+Kalidokit in the browser (later); from-scratch keyframe authoring (the IK rig proper).
6. **Non-goals for v1**: AutoPhysics-class dynamics, facial expression authoring (procedural neutral), contact/ground solving beyond a floor-snap, multi-person (the model supports multi-person renders via multiple "people" in one frame — v2).

**Why small is safe:** the hard part of a pose tool is never the solver — it's matching the consumer's expected render. We own both ends (renderer spec extracted from the trainer's own code), the ecosystem has proven the drag-to-render UX at toy scale (OpenPose Studio), and the model-side contract is a dumb IMAGE input.

## 6. Multi-control composition (the "all-or-selected" requirement)

- **What the union actually is**: one checkpoint, five control *kinds*, **selected by the content of the single control video** — "Union control: one checkpoint handles Canny, Depth, HED, MLSD and Pose control videos for video-to-video generation, no per-condition checkpoint switching" ([card](https://huggingface.co/alibaba-pai/MiniMax-H3-Fun-Controlnet-Union)). There is **no control-type embedding and no per-kind channel packing anywhere** in the H3 pipeline — verified in ComfyUI core (apply builds ≤49 channels from one video + optional mask), the trainer (single `control_file_path` per sample, `control_in_dim` = geometry not kind), and T8mars (`control_kind` is report metadata) **[DOC]**. (Contrast: DiffSynX's Qwen-Image union carries a control-types conditioning embedding; that pattern was *not* carried to H3.)
- **Sanctioned two-signal composition**: control video **+ inpaint mask/source** — the 49-channel layout exists precisely for this pair, and training ran `--enable_inpaint` with random masks **[DOC]**. Product translation: structure-guided regeneration of a *region* is first-class.
- **Simultaneous visual kinds** (e.g. canny + pose): not a trained mode. Two shipped community patterns, both **[COMM]** with **[UNK]** quality vs single control:
  1. **Chained applies** — stack apply nodes; skips sum at the same 5 injection layers. T8mars accumulates prior controls and warns "combined control strength exceeds 1.0; saturation is possible"; RunComfy's recipe: depth 0.3 + pose 0.4 ≈ 0.7 combined, "keep the combined strength near 1.0 or lower"; wyzborrero documents chaining with a shared strength budget. Caveat: T8mars also warns "one owner for the attention/MODEL forward path at a time" — don't pair Fun Control with other forward-patching nodes.
  2. **Composite into one control video** — region-split (T8mars soft_region/box_outline), or blend (e.g. depth background + pose foreground). The model sees one video; per-region kind separation relies on the content itself.
- **Recommendation for our app**: model the requirement as **one control track per shot + optional inpaint mask**; expose "add second control" as chained applies with an auto-combined strength budget (sum ≤1.0, hard warn above), which matches both the node reality and the community recipe; keep region composition as the explicit alternative when the user paints kinds per region.
