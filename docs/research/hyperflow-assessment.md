## 1. WHAT HYPERFLOW IS — the method, precisely

**HyperFlow is Video Rebirth's 8-step LoRA for MiniMax-H3, obtained by data-free flow self-distillation, running on the official diffusers Modular Pipeline.** Diffusers' default is a 50-point sigma schedule = 49 model forwards; HyperFlow performs 8. The base weights, VAEs, conditioner, and workflows (`t2va`, `fl2va`, `ref2va`, all video+audio) stay the official ones — only the LoRA is released. [DOC — upstream README + code read]

It is **not one thing but three reversible additions** [DOC — `hyperflow_h3/blocks.py`, `embedder.py`, `schedule.py`]:

1. **Two-time `(t, r)` interval conditioning — the actual novelty.** Every denoising step is conditioned on the *interval it integrates*, not the point: step `i` runs at `t_i = 1 - sigma_i` aiming at the endpoint `r_i = 1 - sigma_{i+1}`. `TwoTimeEmbedder` wraps the stock `time_embedder`, adds a LoRA'd deep-copy for `r`, and blends: `emb_t(t) + gate * (emb_r(r) - emb_t(t))` with the gate stored in the file header. Conditioning rows (fl2va keyframes, ref2va references) keep `r == t` so they stay pinned exactly as the official denoiser pins them; ref2va *audio reference* rows are never noised (`t == r == 1.0`). **The intellectual lineage is AnyFlow** (Gu et al. 2026, [arXiv 2605.13724](https://arxiv.org/abs/2605.13724), NVlabs — flow-map transition learning `z_t → z_r` over arbitrary intervals, on-policy Flow Map Backward Simulation; explicitly acknowledged in `embedder.py`'s header and the upstream acknowledgements). The category answer: **a flow-map distillation** — the student learns interval transitions (the Euler update block downstream is *unchanged*, so it is still velocity-shaped output integrated by the official loop), which is the axis AnyFlow pitches as fixing consistency distillation's degrade-with-more-steps failure mode.
2. **A fixed 8-step sigma grid stored in the weights file** — 9 points, 8 evaluations, shifted per-modality exactly as the official schedulers do (video shift 12.0, audio shift 3.0): `(1.0, 0.931506, 0.839236, 0.703462, 0.5, 0.296538, 0.160764, 0.068494, 0.0)` — note the symmetry around 0.5. `HyperFlowSetTimestepsStep` installs it on the two official schedulers (an explicit `num_inference_steps` that disagrees *raises*; the step count is the grid's). `HyperFlowLoopDenoiser` hands each step's endpoints to the embedder. Nothing else in the workflow changes — text encoding, VAE, packed layout, Euler update, decoding are the official blocks. [DOC]
3. **(Optional, separable) Sol-Attn sparse attention** — NVIDIA's approximate sparse kernel (Li et al. 2026, [arXiv 2607.24027](https://arxiv.org/abs/2607.24027), `NVlabs/Sana` `techniques/sparse_backends`), applied after 2 dense steps except layers 0–1. Upstream measures it as a real approximation (vs dense: video PSNR ≈ 23 dB, audio waveform cosine 0.88) for a ~7–13% pipeline gain — "check the output before adopting it." We already know this kernel family from the VDN assessment (§1.5 there: scheduled Sol-Attn conflicts with VDN's attention path). **Not part of the quality claims; excluded from our quality arms.** [DOC]

**Adapter shape** [DOC — `lora.py` + upstream README]: PEFT LoRA, **rank 256 / alpha 256, 316 modules, 2.8 GB** — attention projections, feed-forward, token refiner, and *both* time embedders (the base and the endpoint copy; `endpoint_time_embedder.*` keys exist only once `TwoTimeEmbedder` is installed — **it is explicitly not a generic LoRA**; diffusers' `load_lora_adapter` or a stock LoRA loader cannot load it correctly). The file's safetensors header is self-describing (`hyperflow_sigmas`, `hyperflow_gate`, `lora_rank`, `lora_alpha`, `base_model_revision`, tasks). It refuses to coexist with any other PEFT adapter (one fixed adapter; fresh base model required). `disable_hyperflow()` returns the *exact* base model (LoRA off + embedder passthrough move together) — same-seed base/HyperFlow A/Bs are a first-class feature.

**Claims:** 49 NFE → 8 NFE is a ~6.1× forward cut; **measured end-to-end 2.9–3.0× on H200** (4×: ~175 s → ~60 s; 1×: ~395 s → ~130 s for 124 f @ 1344×768) because text encoding + VAE decode are unchanged and become the floor. Peak ~80 GB/card either way in their serving profile (adapter adds 2.8 GB). Quality: the authors' *internal* comparisons against base-at-49-NFE claim **more balanced capabilities, better camera control, better consistency, better materials/detail** — with an explicit "judge on your own prompts" `--baseline` same-seed A/B flag. [DOC — their claim, unverified by us]

**What Sana's sol-engine IS** (the integration context): NVlabs' efficiency-oriented inference codebase for high-resolution video diffusion, built on SGLang's `multimodal_gen` runtime, Apache-2.0, arXiv 2606.23743 — "agent-native" workflow, five reusable acceleration techniques, 2–3× end-to-end across MiniMax-H3 / LTX-2.5 / Sana. The `models/minimax_h3/` subtree carries their production H3 stack (`Sol-H3`: 5 s T2V in 1.653 s warm on 8×B300 with their own FastH3 adapter; `Sol-H3-Spark` for DGX Spark; a 4-step-H3-draft + LTX-2.5-refine "super acceleration" at 22×). The **HyperFlow subtree (PR #507)** is a distinct arm: the *public* Video Rebirth adapter brought onto that runtime — not NVIDIA's fastest H3 path (FastH3 is ~2× faster on the same hardware), but the open, externally-shipped adapter productionized with their optimization stack. The signal for us is institutional: NVIDIA engineers judged HyperFlow worth a fully-provenanced production integration for our exact model family. [DOC]

## 2. THE H3 IMPLEMENTATION SPECIFICS — what NVlabs ships, weights, license

**Files** (`models/minimax_h3/HyperFlow/` on `sol-engine`) [DOC — tree + code read]:

- `hyperflow_h3/` — the six upstream modules, **vendored unchanged** from `Video-Rebirth/hyperflow@1dd2f34` with SHA256s recorded per-file in PROVENANCE.json (verified-equal to the public release; Apache-2.0).
- `sol_hyperflow/` — NVIDIA's resident runtime: `engine.py` (resident 8-GPU lifecycle), `adaln_cache.py` (**paired AdaLN tables** — precompute modulation for every `(t, r)` pair × 4 conditioning variants, then release the original projections), `conditioner_memory.py` (prune to 51 of 64 language layers keeping the pre-normalization `hidden_states[50]` feature + drop the vocabulary head — **bitwise-equal features, 14.23 GB freed per rank** on B200), `runtime.py`/`config.py`/`bootstrap.py`. Reuses `../Sol-H3/` kernels; the guarded `packing` import fallback is the sole change to that shared runtime.
- `infer.py` (CLI: t2v / i2v / ref2va, 5/10/15 s presets = 124/243/362 frames, **eight DiT forwards, no step override**), `validate_runtime.py` (8-GPU functional + native/fused bitwise parity checks), `tests/` (54 CPU tests, no checkpoints needed), `validation/*.json` (machine-readable records), PROVENANCE.json, LICENSE, third-party notices.

**Weights it expects:** the stock `MiniMaxAI/MiniMax-H3` base (pinned `83db0c0efe…`, both `transformer/` and `transformer_ref/` kept distinct) + the official adapter `minimax_h3_hyperflow_8step_v1.0.safetensors` from `videorebirth/hyperflow` @ `a83ec7ad…` (SHA256 `9297f4505bfdef59c3014d11274411809c19b0abfe26161cab2b425a696df447`, published in the repo's `hyperflow.json` manifest). NVlabs ships **no weights of their own** for this. Diffusers pinned at `c419dac0…`. Integration surface is **inference-side only — no retraining, no base-checkpoint surgery**; it is a LoRA + schedule + conditioning wrapper. [DOC]

**Performance at their tier** (8×B300, 1344×768 24 FPS, 8 steps, BF16 unmerged LoRA; median of 5 after 2 warmups; 2026-09-19): T2V 5/10/15 s = **3.571 / 7.685 / 13.273 s**; single-image Ref2VA = **3.773 / 7.608 / 12.578 s** — **2.86–4.15× over the original HyperFlow runtime** (dense SDPA + native PEFT). The speedups include *approximate* SOL/BSA attention, INT8/FP8 transport, and reference-resizing; NVIDIA's own validation doc is explicit that this "does not establish output equivalence or a broad perceptual-quality result" and covers **one prompt, one seed, one reference image** (I2V not benchmarked on B300). Native-vs-fused LoRA parity was bitwise on the tested cases; conditioner pruning bitwise; the *approximate* paths were not equality-checked. This is an unusually honest validation record (their VALIDATION.md is a model of the genre — worth stealing the format for our engine-dependent experiments, as already noted in the Image Studio assessment). [DOC]

**Expected at our tier (544×320-class/864×480-class video, 1K-class stills, 24 GB stack):** no published numbers below 1344×768 — [UNK] for exact figures, but structurally: same 8 NFE as our turbo lane (no step win), adapter adds ~2.8–3.9 GB of weights-class load, and the upstream 1×H200 datum (~130 s for 124 f @ 1344×768 with CPU offload) scales down with resolution and our offload posture. VRAM delta vs the incumbent turbo LoRA should be the same size class; **measure, don't claim** (HF-1 carries the columns). [SPEC]

**License:** code Apache-2.0 everywhere that matters — Sana's tree, the upstream `hyperflow_h3` modules, and the ComfyUI port (below). The **weights are a Model Derivative of MiniMax-H3 under the MiniMax H3 Community License Agreement** (territory excludes EU/UK/KR/US absent MiniMax authorization; AUP applies) — the *same* license that already governs our base H3 and the VDN checkpoints; maintainer-in-Canada territory concern was resolved in the VDN assessment. **No new licensing surface.** [DOC]

## 3. MECHANISM VS OUR STACK — turbo, VDN, two-stage

| | Larryvrh-lineage turbo (our fast tier) | HyperFlow | VDN | Kreatine two-stage (TS-1) |
|---|---|---|---|---|
| What it changes | weights (step-distill LoRA), single-time `t` | weights (flow-map LoRA) **+ interval conditioning + fixed grid** | architecture (trained hybrid attention) + DMD2 turbo | schedule only (raw stage 1 → turbo stage 2, sigma-exact handoff) |
| Distillation family | consistency/step distillation lineage | **flow-map (AnyFlow)**, data-free self-distillation | DMD2 (initialized *from* larryvrh v4) | none (inference scheduling) |
| Steps | 4/8 presets, our `res_multistep`+`simple` pin | 8, fixed grid, **Euler** released recipe, refuses other counts | 8 (deliberately not 4) | N/A (percent handoff) |
| NFE vs our incumbent | — | **same 8 → not a speed lever for us** | 8 + linear-cost attention | same total, split |
| Co-load | XOR with other adapters (ours stacks via strength) | **refuses all other adapters, hard** | XOR (its turbo replaces community turbo) | composes by construction |

- **vs Larryvrh turbo — same slot, different axis, same step count.** Both are LoRA-over-base with a sampler pairing; our registry grammar (`turbo.ts` pairing contract) extends naturally. The differences that matter: (a) HyperFlow conditions on intervals (claimed to avoid consistency distillation's step-scaling droop — though the 1.0 release fixes 8 steps anyway, so that property is latent, exposed only via `ApplyHyperFlowAdvanced` grid overrides); (b) its released sampler pairing is **Euler**, not `res_multistep`+`simple` — a real pairing-contract delta our registry entry must encode; (c) it is **not loadable through a generic LoRA loader** — our `GENERIC_TURBO_ENTRY` fallback would silently mis-load it (backbone deltas without two-time = a *different, off-recipe model*). The standalone drbaph builds exist precisely because stock loaders can't do the two-time half.
- **vs VDN — a different axis that still lands in the same XOR slot.** VDN cuts cost-per-forward (architecture); HyperFlow cuts forwards-needed (distillation) — but at our 8-step turbo tier the forwards are already cut, so HyperFlow competes on *quality at matched NFE*, where VDN competes on *cost at matched quality*. The stacking rule from the VDN assessment extends verbatim: `architecture-patch (VDN) XOR turbo-lora` → HyperFlow joins the turbo side of the XOR (it hard-refuses co-residency with any other adapter, including VDN's). [DOC + our §1.5]
- **vs Kreatine two-stage — conceptual cousins, schedule-slot competitors.** Two-stage *schedules* an interval handoff (raw early for seed diversity/composition, turbo late); HyperFlow *bakes interval awareness into the model* and runs one loop from pure noise. They compete for the same seam (who owns the sigmas). A raw-stage-1 → HyperFlow-stage-2 hybrid is untested and off-recipe (the adapter was trained for the full 8-step trajectory from noise) — [SPEC], not proposed. If HF-1 shows HyperFlow matching the two-stage hypothesis's *goal* (raw-like composition at turbo speed), TS-1's H3 port (node-pack-registry.md §6 order-of-operations item 2) may be pre-empted; if HyperFlow *doesn't*, TS-1 stays live. The two experiments now share a scoreboard.
- **CORRECTION to our working frame:** our fast-path map (speed-quality-and-imagegen-paths.md) reads as "turbo LoRAs (consistency-style) vs VDN vs training-free caching." HyperFlow adds a fourth lever — **flow-map/two-time distillation** — and it is the one NVlabs chose to productionize for H3. Second, smaller correction: "a turbo is a drop-in weights file" is false for this family — the conditioning machinery is inseparable from the weights, which reshapes the integration (below).

## 4. INTEGRATION SHAPE under our architecture — registry-only + ComfyUI

**There IS ComfyUI support — two implementations, both days old** [DOC]:

1. **`Saganaki22/ComfyUI-Hyperflow`** (@ `b4bd9cf`, created 2026-09-19, Apache-2.0; same solo author as the `ComfyUI-VDN-H3` port we already track): ports HyperFlow onto **ComfyUI's native MiniMax-H3 model** — no core files modified, **no custom sampler**. One load-bearing node, `ApplyHyperFlow` (MODEL → MODEL + SIGMAS): applies the LoRA through ModelPatcher (bypass mode = unmerged bf16, matching the reference; merge mode folds the backbone), and **outputs the trained 9-point grid as SIGMAS** — you wire it into `SamplerCustomAdvanced` *in place of* `BasicScheduler`, with **Euler** for the released recipe. `ApplyHyperFlowAdvanced` adds gate/grid overrides (ablations). Weights: converted builds at `drbaph/Hyperflow-Comfyui` — `custom_node_hyperflow_8step_v1.0_comfyui.safetensors` (3.67 GiB, full-base) + pruned variant; self-describing header preserved; the diffusers-layout original is *rejected with a clear message*, never translated at load. Optional `download_if_missing` fetch (off by default — matches our consent posture if we ever flip it on deliberately). Automatic full-base vs pruned-base detection; quantized-base merge path; Sol-Attn maps onto the core Model Sparse Attention node (we exclude it from quality arms).
2. **Standalone LoRA builds** at `drbaph/MiniMax-H3-Turbo-Lora-ComfyUI` — load via the stock `Load LoRA`, nothing to install — **but backbone-only, single-time: output deviates from the released model** (the pack README says this in so many words). These are a *different family*, not a shortcut to HyperFlow.

**The entry, if adopted, is exactly our shape:** weights (a fetch-consent row: the 3.67 GiB converted build + manifests, MiniMax H3 Community License banner — same class as every H3 weights row we already carry) + one `ENGINE_NODE_PACKS` row (Saganaki22 pack, pinned commit, `ApplyHyperFlow`/`ApplyHyperFlowAdvanced` as the instance classes, `detect()` on object_info — our honest-absent degradation turns a missing class into install guidance) + a `TURBO_ENTRIES`-class family whose pairing declares `{sampler: 'euler', scheduler: SIGMAS-from-ApplyHyperFlow, steps: 8, loader: dedicated}` + **builder changes at the seam we already have**: our H3 video chain (`workflow.ts` ~258–275) is `BasicGuider → KSamplerSelect → BasicScheduler → SamplerCustomAdvanced` — the pack targets precisely that grammar; the change is emit `ApplyHyperFlow` at the turbo seam (`ctx.wrapModel('turboLora', …)`) and rewire `SamplerCustomAdvanced.sigmas` from its SIGMAS output instead of node 14. No engine-contract breakage: the graphs remain stock prompt format the real engine honors; goldens + pinned-recipe tests gain the arm. **Nothing deeper than weights + graph — no retraining, no engine forks.**

**Cost honesty (Image Studio precedent for judging third-party machinery):** the pack is small, core-patch-free, custom-sampler-free, and reversible (drop the row + revert the builder branch — modularity contract clean). Risks: **3 days old** (below our 2-week line → this assessment's PROPOSED-PENDING-TEST posture is mandatory, and the pin must be a commit, never a branch); solo author, bus factor 1 (same posture as the VDN port); the `aimdo malloc-graph` compiler-disable note flags patched-forward fragility on some Comfy builds. **Named alternative if the pack disappoints:** a first-party `ApplyHyperFlow` equivalent (embedder + schedule + key remap + ModelPatcher forward patches — pattern-copied from Apache-2.0 code, vendor-legal, our form-adapter precedent; a moderate, not large, job). **Do not** wire the standalone backbone-only builds as "HyperFlow" without labeling the deviation.

## 5. THE TEST DESIGN — HF-1, per the adoption epistemology (directive 426ab190)

**Status: PROPOSED-PENDING-TEST. Suite candidate: the existing harness** (`benchmarks/`, suites + registry + leaderboard + blind-judge bundle — the infrastructure is built; this is a new arm-set on `ref2va-bakeoff` + `tier-ladder`, not new machinery).

**Theory, as a testable claim:** *At matched 8 NFE on the canonical lane (864×480, 124 f, canonical kitchen scene, matched prompt + seed), HyperFlow's flow-map two-time distillation delivers equal-or-better reference identity, prompt adherence, and motion quality than the incumbent fast-tier turbo (larryvrh v4_step600_ema, drbaph pruned), with wall-clock within noise (same NFE, same model) and peak-VRAM delta bounded by the adapter size class.* If true, HyperFlow becomes the fast-tier quality candidate; if false, the incumbent stands and the flow-map axis is parked until a 1.1.

**Arms (A/B/C discipline, one variable — the adapter + its schedule):**

- **A (incumbent):** larryvrh v4_step600_ema 8-step (drbaph pruned, plain loader, `res_multistep`+`simple`) — the measured Ref2VA fast-tier default (bake-off 2026-09-15, task muwufpp: 117 s vs the 20-step anchor's 221 s, identity cos inside the anchor's band).
- **B (candidate):** HyperFlow 8-step via `ApplyHyperFlow` (bypass mode, Euler, released grid, dense attention — no Sol-Attn).
- **C (reference ceiling):** the existing 20-step raw anchor — quality reference, not a candidate.
- **D (follow-ups, only if B ≥ A):** (i) lightx2v 8-step as second incumbent; (ii) **the standalone backbone-only build** — the mechanism-attribution arm: B-vs-D isolates exactly what the two-time conditioning buys over the same backbone deltas single-time.

**Measures — golden domains own the axes; wall-clock + VRAM columns mandatory (cost-scored verdict per directive a3917b4b):** `ref2va-bakeoff` primary (ArcFace identity vs the reference still at f0/f62/f123, blind pairwise vision read, wall-clock per arm) **+ a peak-VRAM column** (nvidia-smi sampling per arm — the suite schema takes the column; the cost table needs it since speed is a wash at matched NFE); `tier-ladder` second (same-seed cross-arm PSNR, motion-timing Pearson/lag/peak-activity — this is where "better camera control / consistency" claims live or die); `movement-md1` optional if the motion claims need the trajectory battery. Prompt adherence rides the blind-read tags; every metric row keeps its known-limits label.

**Gate:** B must beat or tie A on blind-read preference *and* identity-at-reference with no wall-clock/VRAM regression beyond the noise band. Outcome either way is recorded on the leaderboard and this doc gets a DATED addendum — the examined-ledger discipline.

## 6. VERDICT

**ADJUST** — HyperFlow is not "another turbo LoRA" but the flow-map (two-time `(t, r)`) distillation axis for H3 — AnyFlow-lineage, NVIDIA-productionized for our exact model family, with a clean Apache-2.0 ComfyUI surface that targets our exact sampler grammar; at our 8-step tier it is a **quality-side candidate at matched NFE, not a speed win**, so it enters as PROPOSED-PENDING-TEST (HF-1 above), never co-loaded with turbo/VDN adapters, never loaded through a generic LoRA loader.
